# Instructivo Para Contexto IA Del Proyecto Fullness

Este archivo define como mantener el contexto tecnico y de producto para que cualquier IA pueda retomar el desarrollo de Fullness sin depender de conversaciones anteriores.

Regla base del proyecto: nunca poner contexto interno, notas de IA, razonamientos, bitacoras ni instrucciones de desarrollo dentro de la interfaz visible para usuarios. Todo ese material debe vivir en archivos de documentacion como este o en documentos dentro de `contextIA` y `demo-clienta`.

## Objetivo Del Contexto IA

El contexto IA debe servir para:

- Entender el estado actual de la solucion.
- Reconocer modulos, ambitos y decisiones ya tomadas.
- Detectar pendientes reales antes de implementar.
- Evitar repetir trabajo o contradecir instrucciones de la clienta.
- Facilitar el traspaso entre distintos usuarios de IA.

El contexto no debe ser solo historico. Cada actualizacion debe ser retroactiva y proactiva:

- Retroactiva: revisar si lo escrito antes sigue siendo correcto, corregir contexto obsoleto, consolidar duplicados y mover informacion al ambito correcto.
- Proactiva: dejar indicado que impactos puede tener el cambio, que modulos podrian tocarse despues y que riesgos conviene revisar.

## Como Actualizar Este Archivo

Cada vez que se trabaje en el proyecto:

1. Leer este archivo antes de modificar codigo.
2. Revisar los documentos relacionados en `demo-clienta` si el cambio afecta la demo, decisiones de clienta o pendientes.
3. Actualizar el contexto del modulo afectado.
4. Corregir contexto anterior que haya quedado falso, incompleto o ambiguo.
5. Agregar una nota de impacto si el cambio abre una decision futura.
6. Mantener lenguaje claro, directo y accionable.

No usar este archivo como diario cronologico infinito. Si una nota antigua ya no aporta, se debe resumir, reemplazar o eliminar.

## Estado General De La Solucion

Fullness es una demo web hecha con React y Vite para una marca de alimentacion consciente, nutricion emocional y meal prep premium.

La solucion actual incluye:

- Portada visual con video principal local y capa de nutrientes animados.
- Navegacion por secciones.
- Secciones de plato food porn, filosofia, nutricion funcional, como calentar, productos y nutricion emocional.

- Backoffice inicial de menus protegido por `profiles.is_admin`, con gestion de foto, descripcion, precio, ingredientes, descripcion nutricional, alergenos, estado activo y orden.
- Migracion Supabase versionada para menus, carritos, ventas, pagos Mercado Pago, clientes y permisos simples de administracion.
- Assets nuevos de demo: `fullness-lab-hero-0513.mp4`, `fullness-lab-food-porn.png`, `fullness-lab-philosophy.png`, `fullness-lab-hero-video.mp4`, `fullness-lab-logo.png` y `fullness-lab-hero-reference.png`.

La app todavia funciona principalmente como demo visual en carrito y checkout. Hay base Supabase versionada y aplicada, cliente de lectura/escritura de menus y backoffice inicial de menus; falta persistir carrito/checkout desde la UI y completar el flujo productivo de compra.

Direccion nueva entregada por la clienta el 2026-05-12:

## Ambito: Frontend React

Archivos principales:

- `src/main.jsx`: componentes, estado, datos de demo, carrito, cuenta con Supabase Auth y backoffice de menus.
- `src/lib/supabase.js`: cliente publico Supabase para React, usando variables `VITE_SUPABASE_*` o `NEXT_PUBLIC_SUPABASE_*`.
- `src/lib/menu-items.js`: consulta, normalizacion, CRUD y subida de fotos para menus desde `menu_items` y `menu-photos`.
- `src/styles.css`: estilos globales, layout responsive, modales, carrito, backoffice y animaciones.
- `index.html`: punto de entrada Vite y fuentes externas.
- `vite.config.js`: configura React en Vite, expone prefijos `VITE_`/`NEXT_PUBLIC_` y enruta `/api/media` en desarrollo local para poder probar los assets R2 sin overlay de importacion.

Contexto actual:

- La aplicacion esta concentrada en un solo componente `App`.
- `src/main.jsx` mantiene `demoProducts` como fallback local solo si Supabase no esta configurado o falla la carga; cuando Supabase responde, la tienda publica refleja exactamente los menus activos, incluso si no hay ninguno.
- El carrito se guarda solo en estado React.
- La cuenta usa Supabase Auth por correo y contrasena para validar sesion; el permiso admin se lee desde `profiles.is_admin`.
- No hay router ni store global: `#backoffice` abre acceso/backoffice dentro de la misma SPA. No hay backend de checkout; la base Supabase ya esta aplicada y la tienda publica lee `menu_items`.
- El backoffice de menus permite crear, editar, borrar y activar/desactivar menus; edita nombre, slug, SKU, etiqueta, precio, orden, descripcion, foto por URL o subida a `menu-photos`, ingredientes, alergenos, descripcion nutricional y datos nutricionales JSON.
- El video introductorio anterior al hero no debe depender del scroll continuo: una intencion de scroll hacia abajo, touch hacia abajo, teclado o click en el logo central inicia un recorrido automatico de 4 segundos con efecto de scroll/scrub fluido, bloqueando la entrada y el desplazamiento real del sitio durante ese tramo. El video debe cubrir todo el alto visible, el header/menu debe estar oculto mientras corre la animacion y el sitio solo debe aterrizar en el hero al terminar los 4 segundos. Para cuidar la fluidez, la bajada hacia el hero usa reproduccion nativa del video con velocidad calculada, evitando forzar `currentTime` en cada frame. Al terminar, el intro queda consumido y sale del flujo normal: desde el hero no se puede subir al video ni al tramo negro con scroll. En estado `intro-scroll-consumed`, los listeners de wheel, touch y teclado no deben capturar input, para que el usuario pueda seguir bajando normalmente desde el hero. Solo el boton tecnico transparente `Volver a la animacion` reabre el intro y resetea el video.
- El intro muestra el logo Fullness Lab centrado sobre el video, con proporcion cercana al 20% de pantalla y rol de boton accesible. Al iniciar la animacion, el logo debe desaparecer gradualmente, no de golpe. Los cuadros tecnologicos son cuatro tags simples apilados a la izquierda, mas grandes, sin glass pesado ni blur: fondo totalmente transparente, borde blanco y una sola palabra/frase: `Antiinflamatorio`, `Nutrientes`, `Origen de calidad` y `Energia real`. Deben empezar despues del segundo 1 y aparecer uno a uno con efecto de titileo e iluminacion. Al aterrizar en el hero, esos conceptos quedan apilados a la izquierda como bloque estable debajo del boton `Ver mas`, con fondo 100% transparente. El boton `Ver mas` debe compartir el mismo ancho visual de los cuadros tecnologicos y nunca superponerse con ellos.
- El hero es el primer viewport real despues de consumir el intro y no debe depender de ScrollTrigger para hacerse visible. No ocultar `.plate-hero-copy` ni `.plate-hero-visual` con `autoAlpha: 0`, porque puede quedar invisible cuando el intro sale del flujo.
- La imagen/foto del hero debe cubrir todo el alto del hero desde el borde superior; no reservar una franja negra superior para el boton `Volver a la animacion`. Ese boton debe ir absoluto sobre la foto, tambien en mobile, sin participar en el flujo de layout.
- La seccion `#plato` debe funcionar como una escena visual de viewport completo sin texto visible: fondo completo de la imagen de betarraga y una neblina animada usando capas de esa misma imagen, como si fuera un video suave del color betarraga. Mantener el copy en DOM de forma no visible para accesibilidad/SEO, pero no mostrarlo sobre la escena.
- La seccion `Nuestra filosofia` debe sentirse como tierra oscura con raices y magia brillante, no como bloque azul/laboratorio. Usar base cacao/tierra, imagen de raices al fondo y particulas doradas/cobre sutiles con movimiento lento.
- La seccion `Nutricion con fundamento` / `.functional-band` debe mantener su contenido visible por defecto; no dejar sus headings ni cards dentro de animaciones `fromTo` que apliquen `autoAlpha: 0`, porque ScrollTrigger puede quedar desfasado despues de cambios de altura de las secciones anteriores.
- La seccion `Como calentar` / `#calentar` tambien debe mantener visible por defecto su copy, pasos y bolsa visual. No incluir `.heating-copy`, `.heating-visual` ni `.heating-steps` en animaciones que les dejen `opacity: 0` o `visibility: hidden`.
- La seccion `Productos` / `#productos` debe verse como un mockup moderno de menu sobre mesa negra de restaurante sofisticado, con luces LED redondas y tres platos cercanos en carrusel horizontal. Las cards no deben parecer cajas: sin bordes visibles ni fondos de tarjeta; mantener contenido y botones visibles por defecto, sin depender de animaciones `autoAlpha: 0`.
- No usar `overflow-x: clip` en `html` ni `body`: en el navegador embebido puede dejar el root sin desplazamiento vertical usable despues de colapsar el intro. Usar `overflow-x: hidden` para cortar desborde horizontal sin bloquear el scroll del hero hacia las secciones inferiores.
- Las animaciones de contenido despues del hero deben ser no destructivas: nunca usar `autoAlpha: 0` ni `visibility: hidden` como estado inicial de secciones, cards, imagenes o textos clave. Los reveals pueden mover o escalar suavemente, pero el contenido debe quedar visible aunque ScrollTrigger se refresque tarde o una imagen cambie la altura del layout.
- Las anclas de navegacion bajo el header fijo deben tener `scroll-margin-top` suficiente, especialmente `#filosofia`, `#calentar` y `#productos`, para que el salto desde menu no tape titulos ni bloquee la lectura.
- La navegacion interna debe colapsar la intro antes de saltar a una seccion. `#plato` corresponde a la escena visual de betarraga y `#filosofia` debe aterrizar en el bloque de filosofia con texto, no en el contenedor que tambien incluye la escena del plato.

Reglas al modificar:

- Para cambios pequenos, mantener el patron simple actual.
- Si crecen productos, checkout, cuenta o comunidad, evaluar separar componentes y datos por modulo.
- Cualquier texto visible debe ser contenido de producto, no contexto IA.
- Revisar responsive cada vez que se toque header, hero, cards, modales o drawer.
- Mantener dialogos, drawer y menu movil con nombres accesibles, cierre por Escape y botones con `type="button"` cuando no envian formularios.

Pendientes proactivos:

- Separar componentes si el archivo `main.jsx` sigue creciendo.
- Cargar el menu real de la clienta cuando reemplace el seed inicial.
- Persistir carrito si se avanza hacia compra real.
- Probar login admin real con un usuario marcado en `profiles.is_admin` antes de entregar a produccion.
